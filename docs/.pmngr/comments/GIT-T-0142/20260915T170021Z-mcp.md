Closing the criterion the previous review left open: "the derived default `project_id` matches Pando's sanitisation for several sample paths". It is now derived instead of documented.

`internal/server/search_settings.go` gains `searchState.projectID()` and `derivedProjectID(*registry)`: an empty `search.pando.projectId` resolves to `pando.SanitizeProjectID(<path of the first ready mount>)` — there is one Pando per repository, so the mount the search state serves is the path to sanitise. Both consumers use it: the client built in `rebuild()` (`pando.Options.ProjectID`, which is exactly what `SearchCode` falls back to when it is passed an empty project id, `internal/pando/search.go:197-203`) and the settings view. `persist()` still writes the *configured* value, so a derived default is never frozen into the configuration file behind the operator's back. Documentation and the field comment (docs/07-cli-and-api.md:298, internal/config/config.go:490) are now true as written; nothing there needed changing.

Tests (`internal/server/search_settings_test.go`): `TestDerivedProjectIDMatchesPandoSanitisation` — table over four sample paths (`/www/git-in-track` -> `www_git-in-track`, a dotted path, a path with a space, a relative one) plus the no-ready-mount case; `TestSearchProjectIDDefaultsToTheSanitizedMountPath` — GET /api/v1/search/settings reports the derived id, a PATCH that configures an endpoint leaves it derived *and* the constructed `*pando.Client.ProjectID()` carries it, and an explicit `projectId` wins on both.

`go build ./...`, `go vet ./internal/server/...`, `go test -race ./internal/server/... -count=1` and `golangci-lint v2.13.2 run ./internal/server/...` (0 issues) are green.

Reviewer: check the choice of "first ready mount" for a multi-mount workspace — the code index itself is already per mount (`runReindex` passes `m.path` to `IndexProject`), so this default only decides which project an *unqualified* `SearchCode` lands in.
