The value maps this story's settings card configures now reach an actual import, not only the preview.

`vault.YouTrackLink.FieldMap` was a flat `map[string]string`, so `youtrackLinkOf` projected the block through `config.FieldMap.Names()` and every `values:` the user configured stopped at the seam: the preview applied them (`internal/server/youtrackfieldmap.go`) and the import that followed silently fell back to the shipped defaults. It now carries `map[string]mapping.FieldSpec` — field name *and* value map — and `internal/vault` builds its translation table with the new `mapping.FieldMap.WithFields`.

The overlay rule moved into `internal/youtrack/mapping` with it, so preview and import read one implementation rather than two that can drift: a configured map is overlaid on the shipped defaults (a person who mapped one unusual state did not mean to forget what `Fixed` means), keys are folded before the merge, and a blank local value maps nothing. `mapping.FieldMap`'s own rule for a table assembled in Go — supply a value map and you mean exactly it — is unchanged.

Proven by `TestYouTrackImportAppliesConfiguredValueMaps` in `internal/vault`, which renames the state field *and* maps three values, so it fails if either half stops crossing: a value the defaults do not know, a value remapped away from the default, and a value the project said nothing about. Verified to fail on the old behaviour before being kept. `docs/07` §5.5 says the whole block reaches the importer, so a value map is never preview-only.
