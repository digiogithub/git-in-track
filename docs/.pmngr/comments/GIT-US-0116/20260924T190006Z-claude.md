Implemented in jj change on top of the Phase 11 stack (GIT-US-0117). Ready for review.

**Criterion 1 is reinterpreted per the ADR-037 §7 amendment.** It predates the second review
round: a plain verify run no longer writes the spec. The stamp writer is a service with two
callers:

- `requirement.stamp` (vault method): the explicit request `gintrack spec verify --commit` will
  send. The command itself — running the linked tests — is left to GIT-US-0125.
- `(*Vault).stampVerified(ctx, refs, by)`: the function GIT-US-0110 calls from inside its
  done-transition write, after applying the Spec Delta. It reads each requirement from disk
  (`FileStore.GetRequirement`), never refuses, and returns stamped/unstamped lists. The caller
  owns `fs.begin`/`commit`. Vault transition code was not touched.

Each stamp is `{rev: block rev, commit, at, by}`, written through `UpdateRequirement` quoting the
requirement rev, only when every linked test passed at one full commit id.

**Evidence.** Until GIT-US-0141 adds `verify.json`, the evidence is the per-test result cache of
GIT-US-0115 behind `trace.EvidenceSource`. That cache does not record the tested block rev, so
newer results never clear a `text` suspect (only a restamp does), and `at` is the ingest time.
`partial` never counts as a pass. The full mapping is in docs/03 R-REQ-12a.

**Decision for review: drift is measured against the working tree, not HEAD.** The trace graph is
scanned from the working tree, so changed line ranges only map to the right symbols when they
are counted on the same side. An uncommitted edit of a traced symbol also makes the requirement
suspect. On a clean tree the two are the same.

Also for review: a stamp commit missing from the history (a shallow clone) gives `suspect`
(`commit-unknown`), not `passing`.
