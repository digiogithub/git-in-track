Vault and MCP halves landed (`GIT-T-0140`, `GIT-T-0144`, `GIT-T-0153` done): `transfer: {mode, target}` and `dryRun` on `sprint.close`, the new `sprint.transfer` method, and the tools `close_sprint` and `transfer_sprint_items`, with `docs/08-mcp-server.md` §4.14–4.15 and §7.2 updated. `GIT-T-0146` (REST + `sprint.changed`) is still `todo` — `internal/server/` belonged to another agent this wave — and carries a comment with the exact call shapes, the error mapping and the one thing that is easy to get wrong: **a dry run must publish nothing**, so gate `publishWriteSets` on `!result.DryRun` rather than on an empty write set. The story is `in_progress`, not `done`.

Three notes for a reviewer.

**`applyCarries` fixes a latent bug.** The old per-item `carry` wrote the target sprint's file once per reference, so carrying ten items into one sprint produced ten writes of the same file. Target sprints are now mutated in memory and written once each, and `mergeRepoWrites` folds the result into one `RepoWriteSet` per repository — which is what this story's "one `WriteSet` per repository" asks for, and what the REST layer now receives.

**Only `report.Incomplete` is expanded.** `report.Unresolved` — the references no clone and no snapshot could grade — is reported and never acted on: "we could not read it" is not a reason to move someone's work. Finished references are never touched, and an explicit `carry` entry always wins over the bulk mode.

**The completed-target rule is enforced twice.** Once for the whole operation when the bulk mode resolves a target (`sprint_target_completed`, before anything is written, which is what the story asks for), and once inside `carry` so that an explicit per-item `next` into a completed sprint is reported on its own line instead of silently rewriting a finished sprint's numbers. `DerivedStatus` needs a clock, so both call sites take it from `Vault.Now()`; the tests pin it rather than trusting the wall.

`sprint.transfer` edits nothing on the source sprint — `items` keeps every reference it ever held and `committed` is untouched — which matches what a carry decision on close already does.

Tests: `internal/vault/sprinttransfer_test.go` (all four modes across both operating modes, explicit-overrides-bulk, finished work untouched, the completed-target refusal, the uncloned-project line, and a dry run asserted against the rev of every sprint and item plus each sprint's scope) and `internal/mcp/tools_sprints_test.go` through the protocol session. The index fingerprint was tried for the dry-run assertion and rejected: it does not cover sprint files, so it would have passed a test that should fail.

Not done and still open for the snapshot story (`GIT-T-0126`): the snapshot freeze must happen **before** any carry is applied inside `CloseSprint`. The current order is plan → apply carries → write the source sprint, so the freeze belongs immediately after `SummarizeClose` and before the `applyCarries` call in `internal/vault/sprint.go`.
