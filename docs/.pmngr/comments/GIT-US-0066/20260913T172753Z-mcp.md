All four tasks are done, but **this story is left at `in_review`, not `done`**, because one criterion is genuinely half unmet and closing it would put a false entry on the board.

Two real gaps were found and closed in this pass. First, **nothing in `web/` called `createInboxItem`** — the provider method existed in all four providers and no screen offered it, so the inbox could be filled from the CLI and from an agent but not from the application at all. `AddToInboxButton` now sits in the items page header beside *New item* and in the Inbox header, opening a title-plus-optional-body dialog that files with `source: web` and then names the allocated id and links to the queue; it renders nothing for a project with no triage status, the same silence `InboxNavLink` keeps. Three Vitest cases cover submit, the empty and whitespace-only title, and the hidden case. It is placed on the project surfaces rather than the AppShell header because that header is workspace-level and would have needed a project picker — a planning question, which is the one thing this form exists not to ask.

Second, **`land_in_inbox` did not exist in Go at all**, despite `docs/07` §4.17 already implying it worked. The key is now declared, decoding, defaulted and documented (`config.YouTrackLink`, `docs/03` §6 R-INT-7), with `core.InboxLandingStatus` as the shared landing decision that refuses "land in the inbox" on a project with no inbox rather than quietly routing to the backlog. The description's instruction not to add a writer was honoured, and a test pins that a connection save leaves a hand-set `land_in_inbox: true` alone.

**What remains, and why the story is not closed.** The fifth criterion's second clause — "when set, imported items are created with the project's triage status and `inbox.source: youtrack`" — is not implemented: no code in the import write path reads the option. The description assigns that half to GIT-EP-0012, and no task under this story covers it, so it needs a new task there rather than a tick here. `docs/07` §4.17 now says plainly that the importer does not read the key yet, so the docs no longer overstate it.

Also worth a reviewer's eye: `config.YouTrackLink.CommentTemplate` has the same shape of gap — it is in the struct and read, but `setYouTrackLink` never writes it, so a `SaveYouTrackLink` carrying a template silently drops it. Pre-existing, out of scope here, reported rather than touched.
