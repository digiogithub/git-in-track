Landed as `internal/server/youtrackkb.go`: both kinds, the parent-article tree, the four-way change detection and the conflict page, driven by `vault.YouTrackKBParams` as `internal/vault`'s own `YouTrackKBPublish`/`YouTrackKBPull` enqueue it.

Two decisions a reviewer should check. **The pivot of change detection is the fingerprint in `external.key`, not the revs**: both sides are compared against the content that was last published, which is the only way "both changed" is distinguishable from "one changed"; `synced_at` versus the article's `updated` is the fallback for a page with no fingerprint. It matches `internal/vault`'s `kbFingerprint`, so `youtrack.kb.status` and these jobs agree. **The body handed to the transform is read from disk, not from the index**: the indexed `KBPage.Body` has the feedback block stripped (ADR-030), so pulling against it would drop the block on every pull — `rawPageBody` reads the file, `ArticleToPage` re-appends the block, and the write still goes through `kb.write` so `WritePage`'s pruning applies normally.

One gap, reported rather than faked: `ArticlePayload.Attachments` lists the local files a page needs uploaded, and `internal/youtrack` has no article-attachment upload yet, so a page referencing local files is published with a warning naming the count. That is the one thing this story still needs from the client.
