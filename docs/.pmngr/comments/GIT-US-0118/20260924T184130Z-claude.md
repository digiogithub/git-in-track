Implemented in the jj workspace `us-0118` on top of the Phase 11 stack (after GIT-US-0109).

**Criterion 1 is satisfied differently and left unticked for a human decision.** No derived
document per requirement block is sent to Pando, because that is the "push documents to Pando
with `kb_add_document`" alternative ADR-036 rejected: it needs the writing tool the `[AGUI] Tools`
allow-list excludes (it mirrors to disk), and it would duplicate spec files Pando already indexes
— `docs/.pmngr/specs/` is under `KBPath`, so the knowledge-base indexation sees specs even though
the code index skips dot-directories. The story's premise that specs are unreachable only holds
for the code index.

Instead every requirement gets its own row at resolution time: a KB hit on a spec file is located
in the spec's current body (`core.LocateRequirement`, whitespace-insensitive, with head/tail
fallback) and mapped onto the requirement block whose byte range it overlaps most, then answered
as `kind: "requirement"` with the ref as `id`, `spec`, `anchor` (`git-sp-0003-r2`), live `status`
and a snippet clipped to the block. Staleness needs no deletes: ranges come from the current
body, so a chunk of a removed block stays the spec's row, and a changed block is still found by
its head or tail. The reindex job is unchanged.

Trade-off for the reviewer: ranking granularity is Pando's chunk, so two short adjacent
requirements share one embedding. If per-block embeddings are wanted, the path is a Pando-side
feature (heading-aware chunking or a read-only derived index), not a push from gintrack.

`kind: "requirement"`), CHANGELOG Unreleased.
