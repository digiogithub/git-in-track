Implemented as `requirement.list|get|create|update` in `internal/vault` (docs/07 §6.7).

Where the acceptance criteria say "block `rev`", the implementation follows ADR-037 §6 and
docs/03 R-REQ-REV-2: the **write token is the requirement rev** (block text + map entry),
returned as `rev`; the block rev is returned alongside as `blockRev` and is never accepted as a
write token. A write to one requirement never invalidates another's `rev`.

For review: a requirement status change follows the workflow transitions like `item.move`;
`requirement.update` without a rev is `precondition_required` (`"*"` waives); requirement hits
in `search` are opt-in (`requirements: true`) because the web `SearchHit` type does not know the
kind yet. No MCP tool, REST route or web UI (their own stories).
