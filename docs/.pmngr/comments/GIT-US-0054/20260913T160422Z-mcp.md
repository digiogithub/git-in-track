Landed as `internal/server/youtracksearch.go`. The response shape the web client should code against, documented in docs/07 §5.5:

`{projectKey, project, query, preset, limit, items: [{id, idReadable, summary, type, state, assignee, updated, url, linked}], nextCursor}` — `query` is the composed query echoed back so a user sees what their typing became, `nextCursor` is absent on the last page, and `linked` is `null` or `{itemId, type, status, title}`. A `versions` row carries `type: "version"`, `idReadable`/`summary` both set to the version name, and `released`, `archived` and `releaseDate` (a plain `YYYY-MM-DD`); archived values are omitted unless `archived=true`.

Two things worth knowing. **The cursor is opaque** — base64 of the `$skip` — so the paging behind it stays changeable; a client that does arithmetic on it would pin it. **`linked` is built once per request from the index**, not per row: fifty rows would otherwise be fifty dispatch round trips inside one process.

I also added `POST /api/v1/youtrack/import/preview` (synchronous, answering `vault.YouTrackImportPreview`) and `POST /api/v1/youtrack/import` (202 with `{jobId, projectKey, repo, queued: true}`) in `internal/server/youtrackimportapi.go` — the HTTP layer GIT-US-0047 and GIT-US-0059 both assumed and neither owned.
