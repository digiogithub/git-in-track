Both divergences this story's last comment asked someone to decide are now decided, in the data model's favour.

**`attachments[]` holds bare filenames.** `youtrackAttachments` in `internal/vault/youtrack.go` recorded full `.pmngr/attachments/<ITEM-ID>/<name>` paths; it now records the base name, like every other writer (docs/03 §13.4). The reason R-YT-7 gave for the divergence — "an item can be imported before its id is allocated, so a bare name would resolve against the wrong folder" — did not survive reading the code: the function already refused to record anything while `decision.target` was empty, and **nothing ever read those paths**. The download job (`internal/server/youtrackimport.go:downloadAttachments`) builds the folder from `root` plus the item id independently, so the prefix was a second copy of a fact the item id already carries — a second place for it to be wrong, and one the web app would have had to strip. The guard on an unallocated id is gone with it: a bare name is valid whether or not the id is known yet, so a preview now reports the names honestly.

Names are reduced to their base (`youtrackAttachmentName`), which matters more now than before: an entry is read back as a name relative to the item's folder, so `../../etc/passwd` from a tracker must not become a path. `TestYouTrackAttachmentNameIsABareFileName` pins the seven cases.

R-YT-7 in `docs/03-data-model.md` §12.6 is rewritten to state the rule rather than the divergence, the §12.6 table row follows it, and §13.4 gained the cross-reference. What stays true is the timing: the synchronous import records names and the background job fetches bytes, so `W-ATT-MISSING` until it runs.

The `external`-without-`key` observation is unchanged and still correct: only a published KB page records a `key`, and it is a content fingerprint.
