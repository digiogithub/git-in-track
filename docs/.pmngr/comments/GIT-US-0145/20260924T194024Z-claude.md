Both flakes reproduced. A quiet machine did not show them
(`-race -count=10 -cpu 4,8` on gitops, `-count=50 -cpu 1,4,8` on watcher all
passed). Six gitops and four watcher race binaries run at the same time did:

- **internal/gitops**: `TestCommitterDebounceFires` failed in 4 of 6 runs
  ("2 commits" / "3 commits" / "0 commits, want exactly one") and raised 7
  `DATA RACE` reports inside go-git. Trimmed trace:

  ```
  Write by goroutine 48830:
    go-git/v5/storage/filesystem/dotgit.(*DotGit).cleanObjectList()  dotgit.go:529
    go-git/v5/storage/filesystem.(*ObjectStorage).SetEncodedObject()  object.go:131
    go-git/v5.(*Worktree).Commit()  ...  gitops.(*goGitBackend).Commit()
    gitops.(*Committer).fire()  <- gitops.(*Committer).arm.func1()
  Read by goroutine 48831:
    go-git/v5/storage/filesystem.(*ObjectStorage).EncodedObject()
    go-git/v5.(*Worktree).status() ... gitops.(*goGitBackend).stage()
    gitops.(*Committer).fire()  <- gitops.(*Committer).arm.func1()
  ```

  **Root cause:** `Committer` production code, not `ChangedFiles`. Each
  batch's debounce timer runs `commit` on its own goroutine, and a `Flush` runs
  on the caller's. So two commits could run against the same `Backend` at once,
  meaning one go-git `Repository` from two goroutines. That repository is not
  goroutine-safe: `cleanObjectList` resets the object cache while the other
  commit reads it. That is the most likely source of the nil-pointer panic in
  the original report. The race detector caught the unsafe access, but the
  panic itself did not recur in these runs. A second
  bug added commits. When `arm` re-armed a batch whose timer had already fired
  (`Stop` returned false), the stale callback still committed. It committed
  either the batch or a newer batch under the same key, before that batch's
  window ended.

  **Fix:** a per-repository mutex serializes commits
  (`Committer.repoLocks`). A per-batch timer generation (`batch.armed`) means
  only the current timer commits. Regression test
  `TestCommitterSerializesCommitsToOneRepository` failed before the fix and
  passes after it. `TestCommitterDebounceFires` now waits for the `OnResult`
  outcome and does not poll with a 3 s deadline. It enqueues the burst in memory
  inside a 100 ms window.

- **internal/watcher**: `TestWatcherCoalescesRapidWrites` failed in 4 of 4
  runs with `watcher_test.go:224: unexpected extra event {Path:story.md
  Op:write}`. Under load the writer stalled for more than the 200 ms window
  between its two writes, so two batches were the correct output. The test now
  measures how long the writes took and retries any round where they took more
  than a quarter of the window. It never relaxes the one-event assertion. The
  fixed `assertQuiet` sleep is replaced by a sentinel file. The test waits for
  the sentinel's own event, and anything still owed is flushed before or with
  it. `TestWatcherCoalescesAtomicSave` uses the same sentinel.

After the fix the same 6+4 concurrent load passed 10 of 10.
`go test -race -count=50 ./internal/gitops/ ./internal/watcher/` passes.
`docs/06-git-sync.md` §3 now states that commits to one repository never
overlap.

Out of scope, worth a backlog item: `internal/server` shares one
`gitops.Backend` per repository across HTTP handlers (`gitState.backends`), so
status, history or changed-files reads can still reach the same go-git
`Repository` concurrently with a commit. Separately, `internal/server`
`TestSyncJobRetryFromTheDeadLetter` failed in 2 of 3 `make test` runs with
`syncjobs_test.go:287: the retry published "sync.job.started", want
"sync.job.queued"`. It passed 20 of 20 in isolation. This is an event-ordering
flake in the sync-engine test and is unrelated to this change.
