Both problems reproduced before the fix.

- **go-git shared across handlers.** The new test
  `internal/server TestGitRequestsShareOneRepositorySafely` sends item creates
  (commit-on-save with a 1 ms debounce), `GET /git/status`,
  `GET /sync/status`, `GET /sync/conflicts` and `POST /git/commit` from four
  goroutines at once against a go-git repository. Before the fix it failed
  3 of 3 under `-race`. The race detector reported go-git's
  `ObjectStorage.requireIndex` being written by `goGitBackend.Commit` while
  `goGitBackend.Status`, `Identity` (the comment-author lookup in
  `writerIdentity`) and `SyncStatus` read it. The new gitops test
  `TestGoGitBackendSerializesConcurrentCalls` failed too: 72 `DATA RACE`
  reports, and 8 of 20 concurrent commits landed.

  **Fix:** `gitops.Open` now returns the go-git backend wrapped in
  `serialBackend` (internal/gitops/serial.go). The wrapper takes one lock per
  repository around every backend call. Locks are keyed by the canonical
  working-tree root, so two backends opened on the same repository (from the
  root or from a subfolder) share a lock. Every caller is covered, including
  the committer, the sync pipeline, history and conflicts, and no handler
  changed. **Lock order:** `Committer.mu` is held only briefly and never
  across a backend call. It comes before the Committer's per-repository commit
  lock, which comes before the backend lock. The backend lock is a leaf: it is
  taken once, by the wrapper, and `goGitBackend` methods call each other
  unlocked, so the design needs no reentrancy and cannot deadlock. The same
  lock also closes a gap the Committer lock could not: a settings change
  replaces the Committer, and the old one's final flush could overlap the new
  one's commits. The system and jj backends are not wrapped, because each of
  their calls is a child process protected by git and jj lock files. A sync
  run locks per step, so a commit can land between fetch and integrate but
  never inside either.

- **`TestSyncJobRetryFromTheDeadLetter` ("published sync.job.started, want
  sync.job.queued").** This was a real ordering bug in `internal/syncengine`,
  not only in the test. Every state change is announced through `OnJob` after
  the engine lock is released. `RetryDeadLetter` and `Enqueue` broadcast to
  the workers first and announce afterwards, so a worker could announce
  `running`, or even `done`/`failed`, before `queued`. A client was then left
  showing a finished job as queued. The new
  `TestOnJobSeesEachJobsTransitionsInOrder` failed 5 of 5, with sequences such
  as `[queued running failed running done queued]`. The old server test failed
  3 times in 8×600 runs under load.

  **Fix:** `syncengine.announcer` gives each change a turn while the engine
  lock is still held, then runs `OnJob` strictly in turn order without holding
  any lock. The server test now subscribes before it enqueues. It reads the
  job's events from the start of the stream and still asserts that the retry's
  first event is `queued` with `attempt: 0`, followed by `started` and
  `failed`. After the fix, 8×600 runs passed under load.
  Constraint added to the `OnJob` contract: it must not call back into a
  method that changes a job (Enqueue, Cancel, RetryDeadLetter). The server's
  observer only publishes to the hub.

Verified with `go test -race -count=50 ./internal/server/ -run 'Sync|Git'`
(pass, 105 s), run while three gitops race binaries (`-count=10`) ran
alongside it (all pass, 0 races). Four syncengine race binaries
(`-count=50 -cpu 1,4,8`) also passed, as did `make lint` and `make test`.

Docs updated: docs/06 §3.3 (go-git serialization and lock order), docs/07
§5.6 (event order), and CHANGELOG Unreleased/Fixed.
