Finished in wave 2, in `internal/server/pandosync_hub.go`.

- `searchState.followHub(ctx)` registers an ordinary in-process `hubClient` subscribed to `item.changed` and `file.changed`, and drains it. `corpusChangeOf` maps `itemChangedData` (`op: "deleted"` → `ItemRemoved`) and `fileChangedData` with `IsKb` (`op: "remove"`/`"rename"` → `PageRemoved`) onto `pandosync.Event`; anything else is ignored.
- Coalescing: a pending map keyed by repo+kind+document with a 250 ms debounce timer (`corpusDebounce`); the flush replays in hub sequence order.
- **Overflow**: the hub's slow-subscriber drop (`client.overflowed`) is the overflow signal. `followHub` unregisters, runs `Apply(Overflow)` on every exporter — a full re-export — and subscribes again, so a dropped subscriber can never desync silently.
- A write failure is logged in `applyTo` and dropped; the subscriber goroutine lives on and the next event over the same document retries.

Tests: `TestCorpusFollowsHubEvents` (an API edit rewrites exactly that document; a delete removes its corpus file), `TestCorpusReExportsAfterAnOverflow`, `TestCorpusChangeOf` (the mapping table, including "a backlog file is not a page"). The burst-collapses-to-one-write property is already pinned in `internal/pandosync`'s `TestApplyBurstOverTheSameItemWritesOnce`; the debounce here only saves work.

Reviewer: `drainHub` and `corpusChangeOf` in `internal/server/pandosync_hub.go`.
