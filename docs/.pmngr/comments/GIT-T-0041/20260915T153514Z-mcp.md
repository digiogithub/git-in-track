Landed. `RUN_FINISHED{outcome:"interrupt"}` leaves `runStatus: 'interrupted'` and `interrupt: { toolCalls }`, the pending calls read straight off `PandoThread.pendingToolCalls` (id, name, raw `argsText`, parsed `args`). The transcript is untouched — the assistant text that preceded the prompt is still there.

`resume(toolCallId, result)` delegates to `PandoThread.resume`, which appends `{id, role:'tool', toolCallId, content}` after the last user message: exactly the `TrailingToolMessages` shape `deliverToolResults`/`resumeRun` need to re-attach the suspended run rather than start a new one. Same `threadId`, fresh `runId`, events after the resume append to the same message list. The result string is whatever the SDK's HITL helpers build — `approve()`, `deny()`, `answerQuestion()`, `cancelQuestion()` — or arbitrary text for a frontend tool; none of that is re-implemented here.

Fixtures cover both interrupt flavours: `permissionInterrupt` (`pando_permission_request`, narrowed by the SDK's `isPermissionRequest`) with `permissionResumed`, and `frontendToolInterrupt` (a browser-implemented `openItem` call), which is the same wire shape with a different name.

Tests in `store.test.ts`: the park (status, readable pending calls, intact transcript), the full interrupt → `approve()` → finish cycle asserting the posted body (same thread, new run, trailing tool message with `{"approved":true}`), and the frontend-tool variant.
