What the documentation has to say, from the implementation that landed:

- Location: `<cacheDir>/jobs.json`, where `<cacheDir>` is `cfg.CacheDir(configPath)`. The engine takes the directory as a plain `Options.CacheDir` string; an empty one disables persistence.
- Format: one JSON object, `{"version":1,"updatedAt":<RFC3339>,"jobs":[…],"deadLetter":["<job id>",…]}`. Each job is `{id, kind, key, payload, state, attempts, createdAt, updatedAt, nextAttempt, lastError{attempt,class,message,at,retryAfter}}`. Bookkeeping only: no item or page content, and every payload and error string is redacted of credentials before it is written.
- Permissions: the file is 0600 inside a 0700 directory, written as `jobs.json.tmp` and renamed over the target, so a crash cannot leave a half-written journal.
- Retention: `done` and `cancelled` jobs are pruned after `Options.Retention`, default 7 days, at start-up and hourly; failed and dead-lettered jobs are never pruned automatically.
- Delete-safety: it is derived data. Deleting it loses queued work, never user data; a corrupt or unreadable journal is renamed aside (`jobs.json.corrupt-<UTC timestamp>`) and the engine starts with an empty queue.
- Idempotence: replay re-queues jobs that were `running` when the process died, with their attempt count intact, so every `Handler` must be idempotent. This is stated in the package doc comment of `internal/syncengine`.
