Left `todo` on purpose: `web/` belongs to another agent this wave, so the frontend half of GIT-US-0074 was not written here. The server half is on the branch and ready to subscribe to.

The five topics are `sync.job.queued`, `sync.job.started`, `sync.job.progress`, `sync.job.done` and `sync.job.failed`, on the existing `GET /api/v1/events` stream. They share one payload: `{id, kind, key, state, attempt, processed, total, error?, errorClass?}`. `processed`/`total` count the coalescing group — the job's kind plus its key — which is the unit the engine batches by and the unit a progress bar renders. `state` on a `sync.job.done` frame is `done` **or** `cancelled`: a cancelled job is a job that stopped without failing, and both end the row.

Two behaviours the hook has to respect. `sync.job.progress` is coalesced to at most one frame every 500 ms per group, so a count can jump; a terminal frame is never throttled. And a client can still miss frames — the hub disconnects a client that fills its 256-event buffer — so on `stream.overflow`, on `resume.gap` and after any reconnect the hook must **refetch** `GET /api/v1/sync/jobs` rather than trust the stream. That listing answers `{jobs, nextCursor, total, counts, running, deadLetter, engine}` and is the query to invalidate. `docs/07-cli-and-api.md` §5.5 and §5.6 carry the full shapes.

Note that `sync.job.started` is silent today: `internal/syncengine` does not report the queued → running transition through its `OnJob` seam yet. Subscribe to it anyway — the contract is the five topics — but do not build the UI on the assumption that it arrives.
