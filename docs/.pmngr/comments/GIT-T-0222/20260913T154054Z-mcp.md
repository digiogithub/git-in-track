Left `todo`: `cmd/gintrack` is owned by another agent this wave.

`gintrack youtrack kb push|pull <path>` dispatches `youtrack.kb.publish` / `youtrack.kb.pull` with `{project, path, recursive}` and gets back `{project, jobId, pages: [<path>…]}`. Neither blocks: the work is a background job.

Notes for the command:

- `--recursive` maps straight through. A path naming a page selects that page; a path naming a folder selects its direct pages, or every page below it with `--recursive`.
- Without `--wait`, print `jobId` and the selected pages. With `--wait`, follow the job through the sync-jobs API and print page, action and article id.
- **A conflict must not look like success.** `youtrack.kb.status` reports per page `{path, linked, articleId, url, state, syncedAt}` with `state` one of `unlinked`, `in_sync`, `local_ahead`, `remote_ahead`, `conflict`; after a `--wait` run, any page reported `conflict` — or any page the job reported failed — has to exit non-zero so a CI step notices. A both-sides-changed page leaves `<page>.conflict.md` beside it and the original untouched.
- `youtrack.kb.status` also takes `remote: true` to consult the tracker. It is off by default and a `gintrack youtrack kb status` command, if you add one, should keep it behind an explicit flag: it is one request per page.
- Extend the existing `youtrack` parent command in `cmd/gintrack/youtrack.go`; do not create a second one.

The MCP equivalents that landed are `publish_kb_page_to_youtrack` and `sync_kb_page_from_youtrack` in `internal/mcp/tools_youtrack.go`.
