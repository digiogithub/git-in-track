**Reversed by `GIT-EP-0020` — *Pando indexes the repository directly; retire the exported corpus*.** Recorded here so a reader of this closed story finds the reversal (`GIT-US-0099`).

The corpus exporter shipped by this story is deleted: `internal/pandosync`, its hub subscription, the `search.pando.corpusDir` configuration key (a file that still sets it is now **refused by name**), the `corpusDir`/`corpora`/`documents`/`lastExport` fields of `GET /api/v1/search/settings` and the corpus directory input in the settings card. Pando indexes the repository's own committed files instead; the old `<cacheDir>/pando-kb/` directory is not read any more and is safe to delete by hand.

Its two central assumptions were reviewed:

- *"The KB watcher erases front matter on every edit, so `KBWatch` must be `false`"* — **false** for the installed Pando (commit `710a39281`). `internal/rag/kb/watcher.go` contains no write call at all. The bug was real, is documented in Pando's own `internal/rag/kb/repair.go:22-40`, damaged **database metadata rather than files on disk**, and was fixed under PANDO-US-0003/0004. The 523-of-539 measurement was an observation about Pando's database.
- *"Pando's walk has no hidden-directory or `node_modules` exclusion, so `KBPath` must never point at a repository"* — the first half is **true of the knowledge-base walk** and remains the reason `KBPath` is the documentation folder rather than the repository root. The conclusion does not follow (the documentation folder is inside the repository), and the claim is false of the **code** indexer, which skips dot-directories, `node_modules`, `vendor`, `dist`, `build`, `__pycache__` and `.git`.

Accepted cost: filtering by tag inside Pando is lost, because real backlog files carry `labels` rather than the `tags` this exporter synthesised. No derived data is written into source front matter.

Decision record: [ADR-036](../../adr/ADR-036-pando-indexes-the-repository-directly.md). Current documentation: `docs/21-semantic-search.md` §5.
