Closing the criterion "**A hub subscriber overflow triggers a full re-export rather than a silent desync**, and the test drives an overflow to prove it", plus a second desync the rewrite exposed.

**The overflow test now drives the hub.** `internal/server/pandosync_hub_test.go` > `TestCorpusReExportsAfterAnOverflow` runs the real `followHub` against the real `Hub`, waits for it to register, deletes `DEMO-US-0001`'s corpus file behind the exporter's back, and then fills the subscriber's queue through `Hub.Publish` until `deliver` -> `markOverflow` drops it. Making the drop deterministic needed one trick, documented in the test: `drainHub`'s flush resolves the exporter under `searchState.mu`, so the test holds that lock to park the follower mid-flush, publishes `clientBuffer * 2` events into the 256-slot queue, and releases. Crucially every published event is about a *different* item (`DEMO-T-0001`), so the deleted document can only come back through the full re-export — the test cannot pass by an ordinary incremental write. It then asserts the follower re-subscribed (`hub.clientCount() == 1`) and that `followHub` stops with its context. The overflow really trips: the run logs "corpus sync fell behind the event stream; re-exporting the whole corpus". Five consecutive `-count=5` runs under `-race` are green.

**Second fix, found while writing it.** `startCorpusSync` returned early when no exporter existed at start, so a companion started without a corpus and given one through `PATCH /api/v1/search/settings` never started `followHub` — the corpus silently stopped at whatever the enabling export wrote, until a restart. `internal/server/pandosync_hub.go` now splits `armSync(ctx)` (adopts the server's lifetime context) from `syncNow()` (idempotent), and `rebuildExporters` calls `syncNow()` after swapping the map. A full export runs whenever exporters appear or are rebuilt (cheap: the exporter skips unchanged documents by content hash); the hub follower is started at most once per process and resolves the exporter per event, so it never holds a stale one. Both goroutines run under the server's lifetime context, not the settings request's.

Test: `TestCorpusSyncStartsWhenTheSettingsEnableIt` — a companion with no corpus root has no exporter and no hub client; a PATCH setting `corpusDir` runs the full export, starts exactly one follower, and an item edit through the API lands in the corpus without a restart; a second PATCH does not start a second follower.

Verification: `go build ./...`, `go vet ./internal/server/...`, `go test -race ./internal/server/... -count=1` (ok, 24s) and `golangci-lint v2.13.2 run ./internal/server/...` (0 issues).

Reviewer: `syncNow` runs a full export on every settings change, including one that only touches `mcpUrl`. That is deliberate — reconciling is the honest response to a settings change — but it is the one behaviour worth a second opinion.
