Closing the criterion "deleting a thread removes it from storage and **selects a neighbour**". It removed and then always started a blank conversation.

`web/src/features/agent/store.ts` > `deleteThread` now takes the index of the deleted row in the pre-deletion list and selects `remaining[at] ?? remaining[at - 1]` — the row that moved into its place, else the one above it — through `selectThread`. `newThread()` is the fallback for the only two cases that deserve it: nothing survives the deletion, or there is no repository to select within.

Tests: `store.test.ts` — "selects the next thread when the open one is deleted" (three threads, delete the middle one, land on the one after), "falls back to the thread above when the deleted one was last", "starts a fresh thread only when nothing survives the deletion"; `ui/AgentPage.test.tsx` — "selects a neighbouring conversation when the open one is deleted", driving it through the real list rows and the delete confirmation. The pre-existing "lists and deletes threads through the provider" still holds.

`npx vitest run src/features/agent src/features/boards src/api` 430/430, `tsc --noEmit`, eslint and prettier clean.

Reviewer: the neighbour comes from the store's server-listed `threads`, while the sidebar renders `mergeThreadRows(knownThreadIds, threads, meta)` — a locally started, never-sent thread is in the list but not in `threads`, so deleting around one can select a row that is not its visual neighbour. That is a cosmetic ordering difference, not a lost thread; worth a follow-up if it is ever noticeable.
