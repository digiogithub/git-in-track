Landed in `internal/server/search_settings.go`. `POST /api/v1/search/reindex` answers 202 with a job id and runs in the background on a detached context, publishing `search.progress` (shaped like `sync.progress`, phases export/code/kb/completed/failed) and exposing the job through `GET /api/v1/search/settings`. Per repository: full corpus `ExportAll`, then `code_index_project` over the repository working tree via `internal/pando.Client.IndexProject`. Then one knowledge-base pass: `ReindexKB` when a REST URL is configured, otherwise `kbNote` records "Re-exported, awaiting Pando's next import pass" — with `KBWatch` off there is no watcher to trigger, and the handler says so in a comment. A concurrent call is refused with `search_reindex_running` (409) and the running job is untouched; nothing configured at all is `search_not_configured` (400). Export and code-index failures are recorded per repository in separate fields, so a Pando outage never invalidates a corpus export that worked. Tests: `TestSearchReindexExportsAndIndexes` (files on disk, code job id, progress event), `TestSearchReindexRefusesASecondRun`, `TestSearchReindexReportsAPartialFailure`, `TestSearchReindexWithoutAnythingConfigured`.
