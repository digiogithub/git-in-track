Landed the KB sync surface: `kbSyncStatus`/`publishKbPage`/`pullKbPage` on all four providers (browser-only fails loudly), `useKbSyncStatus` + conflict/job invalidation, the toolbar and five-state badge in `KbViewer`, per-node badges in `KbTree` with a folder summary, the folder-publish confirmation with its page count, and `KbConflictNotice`. 64 KB tests; the full web suite is 888 green with lint, tsc, tokens and build clean. `kb_sync` and its direction were added to the YouTrack settings card by the comments agent in the same wave.

The REST paths I built the companion provider against — `GET /api/v1/youtrack/kb/status`, `POST …/publish`, `POST …/pull` with `?key=<projectKey>` — **match the routes another agent landed this wave** in `internal/server/youtrackkbapi.go`, including the 202 on the two queueing routes. No adjustment needed.

Two decisions a reviewer should know. `remote` is a separate cache key rather than a parameter folded into one: "in sync as far as this clone knows" and "in sync, verified against the article" are different claims, and one press of *Check the article* must not make later local reads pretend they were verified. The tree-wide query never sets `remote`, so badging a whole handbook costs no request against someone else's rate limit — a test asserts that. Relatedly, `sync.job.*` invalidation is filtered to the `youtrack.kb.*` kinds, so a long import no longer refetches every page's sync state.

Two seams left. The toolbar does not yet read `kb_sync`, so it always offers both directions manually; when `on_write` is set it should disable or relabel the manual publish, and `features/settings/youtrack-queries.ts` is the hook to read it with rather than growing a second copy. And the documentation half of GIT-T-0219 (`docs/05-web-app.md`, `CHANGELOG.md`) was not done — this wave's web agents were scoped to `web/` because other agents were editing `docs/` in the same working tree.
