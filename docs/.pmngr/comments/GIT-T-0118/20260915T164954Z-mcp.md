## Bug found: the generated `Tools` allow-list makes the gintrack tools unreachable

With the template as generated, three consecutive runs answered *"I can't access the gintrack backlog tools in this session"* — zero `gintrack_*` tool calls, `RUN_FINISHED` with no answer.

Cause, from Pando's source and confirmed live:

- Pando activates the **MCP gateway** whenever `MCPGateway.Enabled || (ToolDiscovery.Enabled && len(MCPServers) > 0)` — `internal/app/app.go:558`. `ToolDiscovery.Enabled` defaults to **true** (`internal/config/config.go:2463`), so configuring `[MCPServers.gintrack]` at all turns the gateway on.
- With the gateway on, MCP tools are **not** registered as `gintrack_<tool>`. Under the unified discovery path only *favorites* are direct, the rest are catalog-only entries reachable through `tool_search` (`internal/llm/agent/tools.go:216-227`, `internal/llm/agent/tool_discovery.go:90-113`); `tool_search` itself is only added when the registry has remote entries, and the gateway catalog is empty in a fresh project DB (`internal/llm/tooldiscovery/policy.go:75-86`). Under the legacy path the tools are `mcp_query_catalog` + `mcp_call_tool`.
- The generated `[AGUI] Tools` list (`cmd/gintrack/templates/agent/pando.toml.tmpl:50-57`) contains only `gintrack_*` and four native names, so `filterAGUITools` strips whichever proxy was present. The glob `gintrack_*` matches nothing in a gateway session — the earlier "the glob is `gintrack_*`, not `gintrack__*`" correction is right about the naming but irrelevant while the gateway is on.

**Configuration that works** (both changes needed; verified by the passing run above):

```toml
[AGUI]
Tools = ['gintrack_*', 'tool_search', 'mcp_query_catalog', 'mcp_call_tool',
         'kb_search_documents', 'kb_get_document', 'code_hybrid_search', 'code_find_symbol']

[ToolDiscovery]
Enabled = false          # write it explicitly: an absent key is not the default here
Mode = 'off'
```
Allow-list alone is not enough (run with discovery left on: still no tools). `ToolDiscovery` alone is not enough either (the proxies are then present but denied). With both, the agent called `mcp_query_catalog` (8 gintrack tools listed) then `mcp_call_tool {"server_name":"gintrack","tool_name":"list_items",…}` and answered correctly.

Consequences a reviewer must weigh, because they change the story's security claims:

- `mcp_call_tool` is a **generic** proxy: it can call any tool on any connected MCP server. Allowing it weakens `[AGUI] Tools` from "the gintrack tools only" to "any MCP tool", i.e. the allow-list stops being the boundary GIT-US-0069 claims. The alternative is registering the gintrack tools as gateway *favorites* so they appear as direct `gintrack_*` names — not something `gintrack agent init` can do today.
- `AutoApprove = false` with `HumanInTheLoop = true` did **not** produce any permission event for the `mcp_call_tool` call: it executed straight through. The "interim boundary is HITL" claim in the story and in docs/20 does not hold for MCP tool calls on this Pando version.
