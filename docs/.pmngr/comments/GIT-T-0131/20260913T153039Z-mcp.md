The client half of this endpoint is now in `internal/youtrack/bundles.go`: `GET /api/v1/youtrack/fields` can project fields *and* their values in one call, which was the hole that blocked the per-value mapping.

```go
func (c *Client) ProjectFieldValues(ctx context.Context, projectID string) ([]FieldValues, error)
func (c *Client) BundleValues(ctx context.Context, setting CustomFieldSetting) (FieldValues, error)
func SupportedBundleType(bundleType string) bool

type FieldValues struct {
    SettingID, Name, FieldType string   // Name is the YouTrack field name, FieldType the id such as "enum[1]"
    BundleID, BundleType       string   // BundleType is the $type, e.g. "StateBundle"
    Bundled                    bool     // false for text/date/integer/period fields and for unknown bundle kinds
    CanBeEmpty                 bool
    EmptyFieldText             string
    Values                     []BundleValue
    Warnings                   []string
}

type BundleValue struct {
    ID, Name, Description, LocalizedName string
    Ordinal      int
    Archived     bool
    Color        BundleColor // ID, Background, Foreground — CSS colors
    IsResolved   *bool       // state values only; nil means the instance did not say
    Released     bool        // version values
    ReleaseDate  Millis      // version values
    AssembleDate Millis      // build values
    Owner        User        // ownedField values
    Login, FullName, Email string // user values
    Type         string      // $type
}

func (v BundleValue) Label() string                  // localizedName > name > fullName > login > id
func (v BundleValue) Resolved() (resolved, known bool)
```

`ProjectFieldValues` is the one call the endpoint needs: it runs `CustomFieldSettings` and then the right bundle endpoint per field — `/api/admin/customFieldSettings/bundles/{enum|state|version|ownedField|build|group}/{bundleID}/values`, and `/user/{bundleID}/aggregatedUsers` for a user bundle, which is the one kind whose members are not under `values`. Fields come back in the order YouTrack lists them.

Two things worth knowing for the REST shape:

- Nothing is silently dropped and nothing fails the whole response. A field with no bundle, or with a bundle kind this client does not know, comes back with `Bundled: false`, no values and one `Warnings` entry saying why; a bundle that cannot be read (403, for instance) leaves the field in place with a warning instead of failing — only a rejected token (401) fails the call, since nothing else would succeed either. A single value with an unexpected shape degrades to its id and name, or is skipped, with a warning. Warnings are already token-redacted; surface them or ignore them, but they are the honest answer to "why is this field empty".
- Map on `Name` and display `Label()`; `Resolved()` gives both the `isResolved` flag and whether the instance actually sent it, which is what the default status proposal in GIT-US-0065 needs (an unknown flag must not read as "not done").

The REST and config shapes are deliberately not designed here — that is this task and `internal/config`.
