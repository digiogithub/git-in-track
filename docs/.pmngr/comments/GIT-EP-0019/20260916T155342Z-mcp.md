**Partly reversed by `GIT-EP-0020` — *Pando indexes the repository directly; retire the exported corpus*.** Recorded here so a reader of this closed epic finds the reversal (`GIT-US-0099`).

This epic's sync model — export every item and KB page to a corpus directory outside the repository, `KBAutoImport = true`, `KBWatch = false` — is gone. `internal/pandosync`, its hub subscription, the `search.pando.corpusDir` key and the corpus fields of `GET /api/v1/search/settings` are deleted. Pando now indexes the repository's own committed files: `[Remembrances] KBPath` is the repository's documentation folder (the backlog under `.pmngr/` included) and the repository root is registered as a Pando **code** project when `gintrack serve` starts.

The premise that forced `KBWatch = false` was **false** for the installed Pando (commit `710a39281`): `internal/rag/kb/watcher.go` performs no file write at all. The bug behind the warning damaged database metadata, not files on disk, and was fixed under PANDO-US-0003/0004. `KBWatch = true` is Pando's own default.

Everything else this epic delivered stands: `GIT-US-0077` (the typed MCP client), `GIT-US-0082` (the search backend behind the core contract), `GIT-US-0086`, `GIT-US-0088` and `GIT-US-0091` are unchanged in substance.

Decision record: [ADR-036](../../adr/ADR-036-pando-indexes-the-repository-directly.md). Current documentation: `docs/21-semantic-search.md` §5.
