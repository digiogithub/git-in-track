**Live check outcome (2026-09-15, GIT-T-0118, two runs).** Everything on the gintrack side works end to end: `agent init`, `agui-serve` accepting the file, the companion proxy (`/info` rewritten, `/health`, threads, cancel 204), the corpus export (352 items, 60 pages) and one full chat turn that called `gintrack_list_items` three times and answered correctly — that turn ran with Pando's MCP gateway on.

Two Pando facts changed the template: (1) with an `[MCPServers]` entry present, ToolDiscovery activates the gateway and MCP tools lose their `gintrack_<tool>` names (they hide behind `tool_search` / `mcp_call_tool`), so the `[AGUI] Tools` allow-list strips them; the template now writes `[ToolDiscovery] Enabled = false, Mode = 'off'` and `[MCPGateway] Enabled = false`. (2) With the gateway off, Pando v0.705.1 deadlocks on the first `gintrack_*` call: `GetMcpTools` caches tool instances bound to the process-wide permission service, so the AG-UI adapter's own service is never consulted and `permissions.Request` waits for a TUI forever. Filed as **PANDO-US-0031** (critical, PANDO-EP-0002). Documented in docs/20 §7 with the interim trade-off (gateway on + `mcp_call_tool`, coarse, no per-tool approval).

The story stays `in_review` until PANDO-US-0031 ships and GIT-T-0118 records a completed `gintrack_*` turn with a `pando_permission_request` round trip. Its other criterion still open is the companion token written literally into `.pando.toml` (Pando does not expand env vars in MCP headers) — a product decision: exclude the file locally (`.git/info/exclude`) and reword the criterion, or drop the header and document a manual paste.
