The token criterion of this story is closed. `gintrack agent init` no longer writes the companion bearer token in clear: it shells out to `pando secret <token>` (`--pando <path>`, `--age-keys <set>`), validates the `age1:` prefix and writes `[MCPServers.gintrack.Auth] Type = 'bearer', Token = 'age1:…'`, which Pando decrypts on load into the `Authorization` header. The `[MCPServers.gintrack.Headers]` block is only written by the explicit `--plaintext-token` escape hatch; with no usable `pando` the command refuses with exit 5 and writes nothing. See GIT-T-0100 (now done) for the evidence and the test names; docs/20, docs/07 §4.18, ADR-035 and the CHANGELOG were updated, including the residual argv caveat (`pando secret` reads no stdin, so the token is briefly visible in the local process list).

What still holds this story open is only the PANDO-US-0031 deadlock, not the token.
