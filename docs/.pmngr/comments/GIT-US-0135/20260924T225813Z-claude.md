Dogfood specs written and traced; the loop runs green. Hold the merge until the release that
ships specs: the first spec raised `docs/.pmngr/project.yaml` to `schema: 2` (a one-line diff,
plus the counter hint `spec: 2`), and binaries up to 2.0.1 do not gate writes on it.

**Specs (created through the tools).** `GIT-SP-0001` "The rev write protocol" (R1–R10) and
`GIT-SP-0002` "Item and requirement ID allocation" (R1–R8), both `in_review`. Each spec was
created with `gintrack item new --type spec --body -` (which reported `schemaUpgraded: 2`), and
each requirement with the MCP tool `create_requirement` over `gintrack mcp --allow-write --agent
claude` on stdio, so `R<n>` was allocated by the tool. Every command ran a binary built from
this change against a throwaway `GINTRACK_CONFIG` that registers only this checkout.

**Markers.** Comment-only `// Implements:` / `// Verifies:` lines in `internal/core` (rev.go,
store.go, comments.go, conflict.go, requirementstore.go, spec.go, allocator.go, ids.go,
indexspec.go and their tests), `internal/vault` (requirement.go and its test) and `internal/mcp`
(errors.go, tools_specs.go, locking_test.go, tools_specs_test.go). One non-comment change was
needed: `TestLoadProjectConfigDogfood` pinned `schema: 1` for this repository's own
`project.yaml`, and it now expects 2.

Both reports and `verify.json` stay outside git (scratch directory; `**/.pmngr/verify.json` is
ignored). Ingest the results after a `jj` snapshot. If you ingest before one, the recorded
commit is older than the working tree, and every requirement whose marker lines changed reads
`suspect`.
