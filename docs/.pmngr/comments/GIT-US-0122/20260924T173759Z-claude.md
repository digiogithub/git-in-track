Implemented in `internal/mcp/tools_specs.go`: `list_requirements` (read), `create_spec`,
`create_requirement` and `update_requirement` (writes), and `get_item` on a requirement ref.
Counts are now 9 read-only / 27 with `--allow-write`.

**Deviation from the criteria wording, per ADR-037 §6:** where the criteria say "block `rev`" as
the write token, the tools use the **requirement rev** (`rev`, block plus `requirements:`
entry). Every read and write returns both hashes, `rev` and `blockRev`; `update_requirement`
quotes `rev` only, and quoting `blockRev` is refused as `stale_revision`. The per-block
protocol the criteria ask for holds: a stale rev on one requirement fails with `currentRev`,
`conflicts[]` and `retry`, while a write to a sibling requirement of the same spec succeeds.

Reviewer decisions:

- `update_requirement` does not accept `verified` nor `unset: ["verified"]`: ADR-037 §7
  reserves the durable stamp for a done move of implementing work or `gintrack spec verify
  --commit`.
- `list_requirements` with neither `project` nor `spec` goes to the workspace's default
  repository, the same routing `list_items` has today (no workspace fan-out).
- Write results omit the block text, path, anchor and line; `changed` names the file.
