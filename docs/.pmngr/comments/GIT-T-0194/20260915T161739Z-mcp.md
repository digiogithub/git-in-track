Landed in `internal/mcp/tools_search.go` (+ `tools_search_test.go`).

- `SearchSemanticInput{query (required), limit 1..20 default 10, project, kind "item"|"page"}` and `SemanticHits{hits, engine, degraded?}`, both with `jsonschema` tags, so the SDK publishes the schemas in `tools/list`.
- One `register(s, toolDef{Name:"search_semantic", Untrusted:true}, searchSemantic)` from `registerSearchTools`, called by `registerTools` (`tools.go:30`). No `Write`, so it is advertised on a read-only server; the untrusted-content note is appended by `register`.
- The handler only validates (`invalidField` on an empty `query`, on a `kind` other than item/page; the limit is clamped like `boundedLimit`), dispatches `search.semantic` and projects hits through `wire.Hit`, filling each hit's current `rev` (and `status` for items) the way `search_items`/`search_kb` do.
- Unavailable backend: the vault's `unavailable` passes through `fromVault` and `semanticFailure` rewrites it with a `retry` telling the agent to fall back to `search_items`/`search_kb`/`list_items` and *not* to report that nothing matched. New code constant `codeUnavailable` in `errors.go`.
- `semanticAnswer.UnmarshalJSON` accepts both the array the core method answers today and the `{hits,engine,degraded}` object the REST surface answers, so `degraded` is not silently dropped if the contract gains it.

Tests (`TestSearchSemantic`, through the in-memory client harness with a stub `vault.SemanticSearcher`): hit with rev/status/snippet and forwarded arguments, empty result, limit default and cap, `kind` scoping, unavailable backend, invalid `query`/`kind`. Reviewer: the unavailable path and the description wording.
