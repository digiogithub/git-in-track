Left `todo`, and it may now be mostly moot: `internal/server` is owned by another agent this wave, but the enqueue this task describes already happens one level lower.

REST and web writes reach `comment.add` in the vault, and `Vault.autoPushComment` (`internal/vault/youtrackpush.go`) queues the `youtrack.comment.push` job from there — after the vault lock is released, and with `context.WithoutCancel(ctx)` so a closing HTTP response cannot cancel it. No inspection of the `WriteSet` in `publishWrite` is needed, and doing it there too would double-enqueue.

The no-feedback-loop guard is the comment's own `external` reference rather than a changed-field check: a comment that already carries a YouTrack id is never queued again, so the push job's write-back of that id cannot re-trigger a push. That is strictly stronger than guarding on the write set, because it also holds for a comment re-written for any other reason.

What is left for `internal/server` is only to install the seam — `SetYouTrackEnqueuer` — and to carry `push_comments` into `vault.YouTrackLink.PushComments`. See the comment on GIT-T-0164.

Recommend closing this as covered by GIT-T-0164 + GIT-T-0171 once the server wiring lands, rather than implementing a second enqueue path.
