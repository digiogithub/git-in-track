Landed as `errors.go` (classification and redaction) and `retry.go` (`RetryPolicy`) in `internal/syncengine`, wired into the engine's completion path: a retryable error re-queues the job on a clock timer with `NextAttempt` set, a terminal one fails it on the spot, and an exhausted one lands in the bounded dead-letter list with its error record intact. `DeadLetter()`, `RetryDeadLetter(id)` and `ClearDeadLetter()` are the surface the REST wave will serve, and `Snapshot().DeadLetterEvicted` counts what the bound dropped.

Two notes for the reviewer and for whoever writes the YouTrack handlers. The classifier reads only interfaces declared in the engine (`StatusCoder`, `RetryableError`, `TerminalError`, `RetryAfterProvider`, `RetryAfterHeaderProvider`) plus the `ErrTerminal`/`ErrRetry` sentinels, so nothing imports the client — but `youtrack.APIError` carries its status in a **field**, not a method, so a handler must wrap it (`syncengine.Terminal(err)`, `syncengine.RetryAfter(err, d)`) or the caller must set `Options.Classify`; giving `APIError` a `StatusCode() int` method would make it work with no wrapper at all, and that one-line change is in a package this wave does not own. Redaction runs on the way into the error record, not only on the way to disk, so a token that leaked into an error string never reaches the API, the UI or the journal — asserted by a test.
